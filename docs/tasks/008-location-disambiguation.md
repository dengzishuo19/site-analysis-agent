# 派工单 008：定位歧义处理——含糊输入不再静默定位到市中心

状态：已完成并验收（有说明的偏差，见文末；用户选择：A 弹候选、仅在相距 >300 m 时对多候选弹选择、只修定位不做噪点过滤）

## 背景（用户在试用中发现的 bug）
输入“北京建筑大学”（该校有西城、大兴两个校区，用户没有指定），系统定位到了“北京市（116.407, 39.904）”——北京市政府旧址附近，并基于这个错误的中心点输出了完整的统计、地图与简报。结果看起来“正常”，实际完全不是用户要分析的地方，**会误导使用者**。

**根因（已用真实接口复现）：**高德地理编码在无法确定具体地点时，会静默返回一个“行政区划中心点”（本例 `level=省`、`formatted_address=北京市`），我们的代码只检查“是否在北京市内”，没有检查定位精度，就照单全收。高德的关键字搜索接口则能正确给出候选（西城校区、大兴校区）。

**探测得到的事实：**
- 地理编码 `level` 取值杂乱：省、区县、村庄、道路、兴趣点、门牌号、门址、公交地铁站点、住宅区……不能只按“是否兴趣点”判断。
- 输入含糊时“北京建筑大学”与“北京”返回同样的“北京市”，必须**结合输入内容**判断。
- 有的输入有多个相距很远的候选（“长安街”4 个、“北京大学”4 个）。
- 关键字搜索的 `parent` 字段可用：校区本身 `parent` 为空，校内子点位（建筑系、食堂、停车场等）的 `parent` 指向校区 ID。

## 要做什么
1. **`lib/geo-resolve.ts`（纯函数，无网络，可单测）**：
   - `classifyGeocode(query, geocodes)`：返回 `ok`（直接分析）、`choose`（需要用户选择）或 `reject`（太宽泛，拒绝并提示）。规则：
     - `level` 属于 {国家, 省, 市, 区县} 且输入是**裸行政区名**（如“北京”“朝阳区”“北京市朝阳区”）→ `reject`，提示“请输入更具体的地点”。
     - `level` 属于 {国家, 省, 市, 区县, 乡镇, 村庄, 开发区, 道路} 且输入不是裸行政区名 → `choose`（说明高德没能确定具体地点，改用关键字搜索给出候选）。
     - 精确 `level` 但**有多个候选且互相距离 > 300 m** → `choose`（用高德地理编码给出的候选）。
     - 其余 → `ok`，取第一个候选。
   - `buildCandidates(pois)`：从关键字搜索结果中只保留 **`parent` 为空的顶层点位**，按名称与坐标去重，限定北京市内，保留高德的相关度顺序，最多 6 个；每个候选含名称、所在区、地址、类型。
   - `distanceM(a, b)`：两点球面距离。
2. **签名的候选令牌（复用 `lib/sign.ts` 的现有函数，可新增函数）**：每个候选携带一个 `pick` 令牌，内容为 {名称、坐标}，用 HMAC 签名并带 30 分钟有效期。选择候选时服务器**验签、验有效期、并要求坐标在北京范围内**，不接受浏览器提交的任意坐标。
3. **`/api/site` 改造（保持向后兼容）**：
   - 输入地址：先地理编码，经 `classifyGeocode` 判断。`ok` → 现有流程；`choose` → 返回 HTTP 200 `{ kind: "choose", reason, query, candidates: [...] }`；`reject` → HTTP 422 与明确提示。
   - 选择候选：`GET /api/site?pick=<令牌>`，验签后以该点为中心做统计，`center.address` 用候选名称。
   - 成功返回的统计数据结构不变（演示数据导出脚本与既有前端不受影响）。
   - 两种请求都走现有的限流与输入清洗。
4. **`lib/amap.ts` 新增**（不改现有函数）：关键字搜索函数（`extensions=all`、限定北京市）；地理编码新增返回 `level` 与全部候选的函数。
5. **页面**：收到 `kind: "choose"` 时显示“‘北京建筑大学’有多个可能的地点，请选择”，每个候选显示名称、所在区与地址，点击后继续原有流程（统计、地图、图表、简报）。收到拒绝时显示明确提示。分析结果里清楚显示“定位到：名称（区）”，并提示“如果不是你要找的地点，请输入更具体的名称”。
6. README 增加“定位精度与歧义处理”一节，写明规则与局限。

## 输入 / 输出
- 输入：用户输入的地址字符串，或候选令牌。
- 输出：统计数据（现有结构）/ 候选列表 / 拒绝提示。
