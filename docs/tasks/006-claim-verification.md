# 派工单 006：校验器升级——从“数字存在”到“断言配对”

状态：已完成并验收（未绑定数字不阻断，方案 A）

## 背景
现有校验器只检查“简报里的数字是否出现在统计表里”。已知漏洞（演示页里已如实展示）：把“地铁站出入口 32 处”手改成“33 处”，而 33 恰好是另一设施的距离，校验通过。此前用外部脚本核对过“名称—距离”配对，多轮真实数据零错配，但这层保证不在代码里。本单把它做进校验器，并度量它到底能覆盖多少简报内容。

## 要做什么
1. **升级 `lib/verify.ts`（保持纯函数、不 import 任何项目模块）**，在原有“未知数字”检查之外，新增三类检查：
   - **名称存在**：每个「名称」必须与统计数据中某个设施名完全一致，否则违规（`unknown-name`）。
   - **名称—距离配对**：「名称」之后、下一个「或句末（。；换行）之前，出现的第一个“数字 + m”视为该设施的距离，必须等于数据中**同名设施**的某个距离，否则违规（`distance-mismatch`，并给出数据中的正确值）。同名设施有多个距离时，任一匹配即可。
   - **类别—数量配对**：类别名（完整标签，及去掉括号部分、去掉“出入口”后缀的简称，如“教育（学校）”“教育”“地铁站出入口”“地铁站”）与“数字 + 处/个/家/座”紧邻（类别名在前，间隔不超过 12 个非数字、非「」、非句末标点的字符；或数字+单位在前、类别名紧随其后，间隔不超过 2 个字符），该数字必须等于该类别的 `count`，否则违规（`count-mismatch`）。`capped` 类别写“不少于 N 处”时 N 必须等于 `count`。
   - 原有检查保留：不在允许集合里的数字为 `unknown-number`。同一处已判为配对违规的数字不重复报告。
2. **对齐位置**：先把「」内的内容替换成等长占位符再做匹配，使所有匹配结果的下标与原文一致；每个违规附带 `span: [start, end)`，用于演示页高亮。
3. **返回结构**（向后兼容，`ok` 与 `violations: string[]` 保留）：
   ```
   { ok, violations: string[],                 // 人可读的违规描述
     issues: [{ kind, text, expected?, span }],
     coverage: { numbers, bound, unbound: [{text, span}] } }  // 覆盖率
   ```
   - “已绑定”指该数字已被名称—距离或类别—数量规则校验过；半径（1000 / 1 km）视为已绑定。
   - 未绑定但存在于允许集合里的数字：**不算违规**，只计入 `unbound`（见文末“待你决定”）。
4. **`lib/report.ts`**：
   - 重试提示改用 `issues` 给出精确纠错（例如“「X」的距离应为 36 m，而你写了 33 m”）。
   - 提示词增加**固定句式**以提高可校验性：类别陈述用“<类别名>共 N 处，最近为「名称」，距离 D m”；列举其他设施用“「名称」距离 D m”。仍禁止计算、推断（原规则不变）。
5. **页面**：`ReportView` 的警告文案由“未通过校验的数字”改为“未通过校验的内容”，逐条列出 `violations`。
6. **静态演示页**：
   - 把新校验器移植进 `demo/template.html`；交互工具用 `span` 高亮违规片段；预设的“注入编造数量”按钮保留，并新增“把某类别数量改成另一个数字”“互换两个设施的距离”“改一个设施名”三个按钮。
   - “校验拦截”里“手改 32→33 无法发现”的说明改为新的、准确的边界描述。
   - 用 `scripts/export-demo-data.mjs` **重新生成**四个案例（新规则下重新校验），重建 `docs/index.html`。
7. 更新 README 的“已知局限”一节与设计要点。

## 验收标准（要有可运行证据）
1. `npm run build` 通过；`npm test` 通过。
2. 单测覆盖：正确配对通过；名称写错被抓；距离写成另一个设施的距离被抓；数量写成另一个数字被抓（“32→33”）；`capped` 的“不少于 600 处”通过、“不少于 601 处”被抓；同名设施多个距离任一匹配通过；类别名在前与数字在前两种语序；一句话里同时出现多个类别各自绑定；「」内含数字不参与；千位分隔符；下标 `span` 与原文位置一致；空文本；未绑定的合法数字不算违规但计入 `unbound`。
3. **对比证据**：取一份真实简报，做至少 6 种篡改（改一个数量、改一个距离、互换两个设施的距离、改一个设施名、把数量改成另一个类别的数量、把距离改成另一个设施的距离），表格展示“旧校验器是否发现 / 新校验器是否发现”。
4. **覆盖率**：对四个案例地址各生成至少 2 份真实简报（共 ≥8 份），统计 `coverage.bound / coverage.numbers`，目标 ≥ 90%；低于则调整固定句式并重测，交付说明写明最终数字。
5. **误报率**：上述真实简报在新规则下应全部通过；出现误报时必须分析是解析器的问题还是模型写法的问题并修正，交付说明写明误报数量与处理。
6. 演示页：移植的校验函数与 `verify.ts` 用 ≥30 条用例对照，行为一致；`file://` 打开无报错；新增按钮均能被新校验器抓出；四个案例全部 `verified: true`。
7. 本地生产模式跑一遍完整流程（输入地址、统计、简报），`verified=true`。
8. 全仓库搜索 Key 与签名密钥前 6 位无结果；`.env.local` 未入库。
9. 交付说明列出：改动文件、各文件作用、验证方法、遇到的问题，以及**新校验器仍然防不住的情况**。

## 待你决定：未绑定的数字要不要阻断
- **A. 不阻断（推荐）**：未绑定但存在于统计表里的数字只计入覆盖率，不判违规。优点：误报少，重试少。缺点：模型若用了校验器不认识的句式，把错数字放在这种句式里，仍可能漏检；用“覆盖率 ≥ 90%”和固定句式来压缩这块盲区。
- **B. 阻断**：除半径外，任何未绑定的数字都判违规。优点：没有盲区。缺点：模型稍微换一种说法就会被判违规，重试和标红会明显变多，用户体验变差。

选 A 的话，覆盖率会成为我们对外讲“校验有多严”的一个真实、可量化的数字。
